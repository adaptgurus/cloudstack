# LayerSentry Kubernetes 1.36 — Stable CAPI/CAPRKE2 Version-Lane Clarification

**Date:** 2026-09-06  
**Scope:** version-selection clarification for Workstream E  
**Architecture change:** none  
**Production certification:** not established

## 1. Important terminology correction

`v1beta1` and `v1beta2` in Cluster API are **API/contract version names**. They are not the same thing as a software release being a prerelease/beta build.

For example:

- Cluster API `v1.13.x` is a stable `1.x` software release line;
- CAPRKE2 `v0.25.2` is a normal published release, not a prerelease;
- CAPRKE2 `v0.25.2` implements the CAPI `v1beta2` API contract;
- CAPC `v0.6.1` is a normal published release but still implements the older CAPI `v1beta1` infrastructure-provider contract.

Current CAPI documentation is moving providers **from v1beta1 to v1beta2** and plans removal of the old v1beta1 contract in a future CAPI release. Therefore choosing the `v1beta2` contract does not mean choosing an experimental CAPI release; it is the forward/current provider contract.

Do not describe the LayerSentry candidate as “using beta CAPI software” merely because Kubernetes object apiVersions contain `v1beta2`.

## 2. Kubernetes 1.36 has more than one fully released CAPI/CAPRKE2 lane

### Lane K36-A — current/forward stable family

```text
CloudStack 4.22.1.1
CAPI       1.13.5
CAPRKE2    0.25.2
CAPC       0.6.1
RKE2       1.36.4+rke2r1
```

Facts:

- CAPI `1.13.x` supports Kubernetes `1.36` workloads;
- CAPRKE2 `0.25.2` is built against CAPI `1.13.5`;
- CAPRKE2 `0.25.2` uses the current `v1beta2` contract;
- CAPC `0.6.1` remains on the older `v1beta1` infrastructure contract;
- CAPI currently provides a temporary compatibility bridge for v1beta1 providers.

Reason to prefer this lane for forward-looking qualification:

- CAPI 1.13 is in the standard support period;
- CAPRKE2 0.25.2 is the current released line;
- it gives a longer upgrade runway than CAPI 1.12.

It is still a qualification candidate because CAPC 0.6.1 is the lagging provider and must pass exact CloudStack 4.22.1.1 tests.

### Lane K36-B — conservative fully released CAPI 1.12 family

```text
CloudStack 4.22.1.1
CAPI       1.12.10   (1.12.8+ supports Kubernetes 1.36)
CAPRKE2    0.24.3
CAPC       0.6.1
RKE2       1.36.4+rke2r1
```

Facts:

- CAPI `1.12.8` and later 1.12 patches explicitly support Kubernetes `1.36` management/workload clusters; `1.12.10` is a published stable patch;
- CAPRKE2 `0.24.3` is a published stable release built against CAPI `1.12.3` and uses the `v1beta2` contract;
- using CAPI `1.12.10` with the same 1.12 provider family is a valid qualification target;
- CAPC `0.6.1` still uses the older v1beta1 provider contract and therefore still relies on CAPI's temporary compatibility bridge.

Reason to test this lane:

- it reduces CAPI/CAPRKE2 family skew and gives us a second all-released Kubernetes-1.36 comparison point.

Reason not to freeze it automatically as long-term production:

- CAPI 1.12 entered maintenance mode in August 2026 and has a shorter remaining support runway than 1.13.

### Lane K36-C — modern CAPC contract lane

```text
CloudStack 4.22.1.1
CAPI       1.13.x
CAPRKE2    0.25.2-compatible
CAPC       v1beta2-contract release, or a reviewed/pinned downstream build based on upstream PR #493 until an upstream release exists
RKE2       1.36.x
```

This removes dependency on the temporary v1beta1 compatibility bridge.

During this validation, CAPC PR #493 remained open/unmerged; therefore this lane cannot be represented as an all-upstream-stable CAPC release yet.

## 3. What we should test first

Recommended E0 order:

1. **K36-A** — preferred forward stable family;
2. **K36-B** — conservative released comparison/reference;
3. **K36-C** — future-proof CAPC contract lane if K36-A exposes bridge limitations or when the upstream CAPC release lands.

Do not choose based only on which version number is newest. Compare:

- controller startup/contract conditions;
- ClusterClass/topology;
- create/delete/scale;
- CAPRKE2 bootstrap/join;
- RKE2 6443 + 9345 endpoint behavior;
- CAPI Machine replacement;
- CAPC volume ownership/data safety;
- CloudStack 4.22.1.1 networking/storage;
- upgrades and controller restarts;
- full air-gap behavior.

The winning LayerSentry production tuple is the one that passes those tests and has the best supported upgrade runway.

---

## 4. If the requirement is “no beta-named Kubernetes APIs at all”

That requirement is not realistic for the current CAPI ecosystem and would not improve production safety.

Avoiding the string `v1beta2` would force us away from the current Cluster API contract and toward one of these alternatives:

- custom LayerSentry lifecycle orchestration using CloudStack native APIs + Ansible/RKE2;
- native CloudStack CKS/kubeadm instead of RKE2;
- another full management platform.

Those alternatives either increase custom Day-2 lifecycle code or fail the LayerSentry RKE2/full-air-gap requirement.

The production question should therefore be:

> Is the exact released provider tuple supported, tested and safely upgradable?

not:

> Does an internal Kubernetes API version contain the word `beta`?

---

## 5. Frozen decision after this clarification

- architecture remains CAPI/CAPC/CAPRKE2/RKE2;
- do not use an unmerged CAPC PR by default;
- test released stable Lane K36-A first;
- test released stable Lane K36-B as a comparison;
- use a downstream/unreleased CAPC v1beta2-contract build only when needed and only with exact review/evidence;
- keep CAPC v1beta1 bridge removal on the upgrade roadmap because CAPI plans to remove old-contract support in a future release;
- no version tuple is `PRODUCTION_CERTIFIED` until E0 passes.
